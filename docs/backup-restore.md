# Backup and restore

> An untested backup is a guess. `./scripts/restore.sh` is scripted so that
> proving this works is a two-minute job, not a project.

## Why the NAS is not a backup

The photo library lives on the NAS, and that is one copy, not a backup. A
deleted album, a failed volume, a bad mount or a mistaken bulk delete in the
Immich UI propagates to it immediately. Phones are not the second copy either:
once photos are offloaded to free up space, the NAS holds the only full-
resolution originals.

This is the offsite copy: encrypted with restic, in S3-compatible object
storage, on a daily timer, verified weekly.

## What has to be backed up

Everything below is under `UPLOAD_LOCATION`
(`immich_data_mnt/immich/library`) unless stated otherwise.

| Path | Backed up? | Why |
|---|---|---|
| `library/` | **Yes - critical** | The originals, when the storage template is on. Irreplaceable. |
| `upload/` | **Yes - critical** | The originals when the storage template is off, plus uploads in flight. |
| `profile/` | Yes | Profile images. Tiny. |
| `backups/` | **Yes - critical** | Immich's own database dumps: albums, people, faces, metadata, shared links, users. Photos without this are a folder of files. |
| `thumbs/` | No | Regenerated by the Generate Thumbnails job. Set `BACKUP_INCLUDE_THUMBS=true` to include them. |
| `encoded-video/` | No | Regenerated by the Transcode Videos job. Set `BACKUP_INCLUDE_ENCODED_VIDEO=true` to include them. |
| `local_data_mnt/immich/postgres` | **No - deliberately** | Copying the files of a running Postgres does not produce a restorable database. The dumps in `backups/` are the database backup. |
| `local_data_mnt/immich/model_cache` | No | Cache. Re-downloaded on demand. |
| `local_data_mnt/immich/restic-cache` | No | Cache. Rebuilt on demand. |
| `.env.bash` | **Yes - separately** | Secrets. Includes `RESTIC_PASSWORD`, so it cannot live only inside the backup it unlocks. |
| `generated_config/` | No | Regenerated by `./create-systemd-service.sh`. |

Excluding `thumbs/` and `encoded-video/` trades restore time for storage cost:
a restored library is fully usable, but browsing is slow until the thumbnail
job catches up, which takes hours on a large library.

Immich writes a `.immich` marker file into each of these directories and looks
for it at startup, so that a library which failed to mount is not mistaken for
an empty one. Leaving a directory out of the backup entirely is safe - Immich
recreates it, marker and all. Creating one by hand without the marker is not:
the server then refuses to start.

### The `RESTIC_PASSWORD` trap

The repository is encrypted with `RESTIC_PASSWORD`, which lives in `.env.bash`
on the server. **Without it the backup is unrecoverable.** If the only copy is
on the machine the backup exists to protect, there is no backup.

Store it somewhere unrelated: a password manager, or on paper. Not in this
repo, not on the NAS, not in Immich.

Back the rest of `.env.bash` up by hand, separately, whenever it changes:

```bash
gpg -c --output ~/immich-env-$(date +%F).gpg .env.bash
# then move that file somewhere off this machine
```

## One-time setup

1. **Create the bucket and an access key** at the provider. Use a bucket and a
   bucket-scoped key that are not shared with any other backup, so the two can
   be revoked and retained independently. The bucket must already exist -
   restic creates the repository inside it, not the bucket itself.

2. **Fill in `.env.bash`**: `S3_ENDPOINT`, `S3_BUCKET`, `AWS_ACCESS_KEY_ID`,
   `AWS_SECRET_ACCESS_KEY`, `RESTIC_PASSWORD`, and `DISCORD_WEBHOOK_URL` if
   alerting is wanted.

3. **Turn on Immich's database dumps**, under Administration -> Settings ->
   Backup Settings. They default to 02:00, which is before the backup timer at
   04:00 - that order matters (see below). `scripts/backup.sh` fails if the
   newest dump is more than `IMMICH_DB_DUMP_MAX_AGE_HOURS` old.

4. **Install the units and run the first backup by hand.** It uploads the whole
   library and can run for days; `RESTIC_UPLOAD_LIMIT_KIB` keeps it from
   saturating the connection. It is safe to interrupt - restic writes its index
   as it goes, so the next run continues rather than starting over.

   ```bash
   INSTALL=true ./create-systemd-service.sh
   ./scripts/backup.sh
   ```

5. **Verify it, then enable the timers.**

   ```bash
   ./scripts/restore.sh                 # must print PASS
   sudo systemctl enable --now immich-backup.timer
   sudo systemctl enable --now immich-check.timer
   systemctl list-timers 'immich*'
   ```

## Backing up

```bash
./scripts/backup.sh                  # also on a daily timer at 04:00
sudo systemctl start immich-backup   # same, via systemd
```

It initialises the repository on first run, checks the database dump is fresh,
snapshots the library, applies the retention policy with `--prune`, and
finishes with a structural check.

It **refuses to run if the NAS is not mounted.** An unmounted CIFS mount point
is an empty directory that looks exactly like a library with no photos in it.
Backing that up would record an empty snapshot, and after enough days retention
would age out the last good one - turning a mount failure into real data loss.

### Order matters: database first, files second

Immich dumps its database at 02:00; the backup runs at 04:00. That way the
snapshot contains a dump that is older than the files, never newer. A photo
uploaded between the two shows up after a restore as a file Immich does not
know about, which Administration -> Repair lists and which costs nothing. The
other order produces database rows pointing at files that do not exist, which
is a broken library.

If the dump job stops running, `backup.sh` still takes the snapshot - photos
are worth capturing either way - and then exits non-zero so the failure
alerts. A backup holding photos and no albums is the failure mode worth being
loud about.

### Why the first run is the slow one

restic deduplicates and photos are written once and never modified, so after
the initial upload only genuinely new assets are sent. The daily run is a
metadata scan plus a few hundred MB.

That scan is the part to watch on CIFS. restic decides a file is unchanged from
its size, mtime and inode number, and CIFS inode numbers are assigned by the
client and can change across a remount. When they do, restic re-reads the whole
library over SMB: nothing is re-uploaded, but the run takes hours.
`RESTIC_SCAN_FLAGS="--ignore-inode"` drops inode numbers from the comparison.
Check it is working by looking at the second run's summary:

```
Files:  0 new,  0 changed,  48213 unmodified
```

If most files show as changed run to run, add `--ignore-ctime` as well.

### Switching providers

`RESTIC_REPOSITORY` is built from `S3_ENDPOINT` and `S3_BUCKET`, so any
S3-compatible provider works by changing those two values:

```bash
export S3_ENDPOINT="https://ca-central-1.linodeobjects.com"   # Linode
export S3_ENDPOINT="https://s3.us-west-004.backblazeb2.com"   # Backblaze B2
```

On Backblaze, set a lifecycle rule to keep only the last version of a file (or
prior versions for a fixed number of days). B2 keeps every version by default,
which means `prune` frees nothing and the bill grows forever.

## Verifying a backup

```bash
./scripts/check-backup.sh                       # also on a weekly timer
RESTIC_CHECK_SUBSET=5% ./scripts/check-backup.sh
```

`restic check` on its own only validates metadata and structure - it will
happily pass on a repository whose data blobs are unreadable.
`--read-data-subset` is the part that downloads data and verifies checksums.

By default the script re-reads the slice `<week number>/53`, which walks a
different fifty-third of the repository each week and covers all of it in a
year. A percentage would re-read a random share every week, so some packs would
be read repeatedly and others never. At terabyte scale that distinction is the
difference between eventually reading everything and eventually reading most
things.

## Test restore

The default mode restores a handful of random photos and the newest database
dump - a few hundred MB, not the whole library - and checks what comes back:

```bash
./scripts/restore.sh                 # sample verification
./scripts/restore.sh --samples 20    # more photos
./scripts/restore.sh --snapshot 1a03f918
./scripts/restore.sh --full          # everything, to a scratch dir
```

It picks the sample from Immich's own database and compares the restored bytes
against the SHA-1 checksum Immich recorded when the photo was uploaded:

```
Sampled 5 assets from asset.
Newest database dump in the snapshot: immich-db-backup-...-v3.2.0-pg14.sql.gz

=== Verification ===
  ok       IMG_4417.HEIC  (2.8M)
  ok       DSC_0031.jpg   (7.1M)
  ...
  5 of 5 sampled photos restored with matching checksums
  (0 corrupt, 0 missing)

  database dump ok: gzip valid, 96 CREATE TABLE statements

PASS: photos and database dump both restore intact.
```

Matching checksums are a stronger claim than matching file counts: they prove
the bytes came back unaltered, not merely that files exist. The dump check
proves the other half of a restorable Immich is in the snapshot too. The script
exits non-zero on anything short of `PASS`.

## Full recovery

Rebuilding from nothing.

1. Work through the installation steps in the [README](../README.md) on the new
   server: group, Samba credentials, `.env.bash` (from your offsite copy), local
   directories, units. **Do not start Immich yet.**

   `IMMICH_VERSION` must be the release that wrote the dump - it is in the dump
   filename. Restore on that version, then upgrade afterwards. The paths in
   `.env.bash` must match the old server's, because snapshots store absolute
   paths.

2. Mount the share and restore the library in place:

   ```bash
   sudo systemctl start home-hugo-immich_iac-immich_data_mnt.mount
   mountpoint immich_data_mnt          # must be mounted first
   ./scripts/restore.sh --in-place     # asks you to type RESTORE
   ```

   Ownership on a CIFS mount comes from the mount options
   (`uid=${mount_user}`, `gid=${mount_group}`), not from the restored files, so
   there is no `chown` step.

3. Start **only** the database, and load the newest dump that came back:

   ```bash
   source .env.bash
   docker compose -f compose/immich/docker-compose-immich.yml up -d database
   ls -la immich_data_mnt/immich/library/backups/
   ./scripts/restore.sh --db immich_data_mnt/immich/library/backups/<newest>.sql.gz
   docker compose -f compose/immich/docker-compose-immich.yml down
   ```

   `--db` refuses to run while `immich_server` is up, checks the dump's gzip
   integrity before dropping anything, and handles both the `pg_dump` and
   `pg_dumpall` shapes Immich has used.

4. Start the stack and watch it come up:

   ```bash
   sudo systemctl start immich
   docker logs -f immich_server
   ```

5. Regenerate what was deliberately not backed up, from Administration ->
   Jobs: **Generate Thumbnails**, then **Transcode Videos**. Browsing is slow
   until the first finishes. Machine learning data - faces, people, CLIP search
   - is in the database and comes back with it; it does not need re-running.

6. Run **Administration -> Repair**. It lists files on disk the database does
   not know about (photos uploaded between the dump and the snapshot) and
   database rows whose files are missing (which should be none).

7. Spot-check: log in, open an album, view a full-resolution original, and
   compare the asset count against what you remember.

### If only the local disk was lost

The library and the dumps are on the NAS and are fine, so object storage is not
involved. Recreate `DB_DATA_LOCATION` and `IMMICH_MODEL_CACHE_DIR`, start only
the database, load the newest dump from
`immich_data_mnt/immich/library/backups/` with `./scripts/restore.sh --db`,
then start the stack. The model cache re-downloads itself.

## Alerting

`immich.service`, the mount unit, `immich-backup.service` and
`immich-check.service` all carry `OnFailure=immich-alert@%n.service`, so a
failure posts to Discord with the last 25 journal lines.

More importantly for backups, `check-backup.sh` posts a **weekly heartbeat** on
success (`DISCORD_HEARTBEAT="true"`), including the latest snapshot and
repository stats. A backup system that only speaks up on failure cannot be
distinguished from one whose timer stopped running months ago - the heartbeat is
what makes silence meaningful.

If the heartbeat stops arriving, check:

```bash
systemctl list-timers 'immich*'
sudo journalctl -u immich-check -n 50
./scripts/notify-discord.sh --test
```

## What this does not protect against

The server holds an access key that can delete the bucket, so anything that
compromises the server can destroy the backup. Bucket versioning with a rule
that keeps deleted versions for a few weeks closes that gap cheaply, at the
cost of paying for deleted data until the rule expires it. Not configured here.
